## 摘要
近期工作将递归自我改进（RSI）扩展到面向长时程编码和终端任务的智能体执行框架，使智能体能够从经验中改进执行机制。然而，可泛化的执行框架 RSI 仍具挑战性。首先，在评估基准或其子集上演化执行框架，难以区分可复用的改进与针对特定基准的适配。其次，单轨迹更新可能将系统性的执行框架缺陷与实例特定的推理和求解细节混为一谈，从而产生难以迁移到未见任务的修改。第三，在单体式执行框架中定位反复出现的行为缺陷十分困难，而整体执行框架优化可能纠缠不相关的机制，并使归因与验证复杂化。我们提出 ModularRSI，一个面向可泛化执行框架演化的、与基准不相交的、对比式且模块化的框架。ModularRSI 对同一任务的成功与失败轨迹进行对比，并跨任务聚合证据，以识别反复出现的行为缺陷。它将可演化的执行框架分解为五个功能模块：智能体循环（Agent Loop）、工具使用（Tool Use）、观测管理（Observation Management）、上下文管理（Context Management）和任务完成检测（Task Completion Detection）。每个模块在受限的修改范围内独立演化，随后进入集成阶段，将演化后的模块组合为统一的执行框架并解决潜在冲突。为支持与基准不相交的演化，我们整理了 2,000 个来自外部来源的可执行演化任务，这些任务与下游评估基准不相交。在 TB2.0 和 SWE-Bench Verified 上的实验表明，在未见的域内和跨域任务上均取得一致提升，且演化后的执行框架还能迁移到不同的基础模型。

## Abstract
Recent work extends recursive self-improvement (RSI) to agent harnesses for long-horizon coding and terminal tasks, enabling agents to improve execution mechanisms from experience. However, generalizable harness RSI remains challenging. First, evolving harnesses on evaluation benchmarks or their subsets makes it difficult to distinguish reusable improvements from benchmark-specific adaptation. Second, single-trajectory updates can conflate systematic harness deficiencies with instance-specific reasoning and solution details, producing modifications that transfer poorly to unseen tasks. Third, localizing recurring behavioral deficiencies within monolithic harnesses is difficult, while whole-harness optimization can entangle unrelated mechanisms and complicate attribution and validation. We propose ModularRSI, a benchmark-disjoint, contrastive, and modular framework for generalizable harness evolution. ModularRSI contrasts successful and failed trajectories for the same task and aggregates evidence across tasks to identify recurring behavioral deficiencies. It decomposes the evolvable harness into five functional modules: Agent Loop, Tool Use, Observation Management, Context Management, and Task Completion Detection. Each module evolves independently within a restricted modification scope, followed by an integration stage that combines the evolved modules into a unified harness and resolves potential conflicts. To support benchmark-disjoint evolution, we curate 2,000 executable evolution tasks from external sources that are disjoint from downstream evaluation benchmarks. Experiments on TB2.0 and SWE-Bench Verified show consistent improvements on unseen in-domain and cross-domain tasks, with the evolved harness also transferring across different foundation models.

# ModularRSI 论文总结

## 1. 核心问题与整体含义

- **研究背景**：CLI 智能体在长时程软件工程与终端任务上表现突出，其效果越来越依赖于"执行框架"（harness）——即控制执行流程、工具交互、上下文管理与环境反馈的机制层。近期工作将递归自我改进（RSI）扩展到 harness，使智能体从执行经验中改进执行机制。
- **核心问题**：可泛化的 harness RSI 仍面临三个相互耦合的挑战：
  - **数据层面**：现有方法多在评估基准或其子集上演化，难以区分"可复用改进"与"基准特定适配"；高质量可执行演化数据构建成本高。
  - **轨迹层面**：单条轨迹将系统性 harness 缺陷与实例特定的推理/求解细节纠缠，易产生无法迁移的任务特定修改。
  - **机制层面**：单体式 harness 中难以将反复出现的缺陷定位到具体组件；全 harness 优化会纠缠无关机制，导致归因与验证困难。
- **整体含义**：论文提出 **ModularRSI**，一个"基准不相交 + 对比式 + 模块化"的 harness 自演化框架，旨在把粗粒度的任务级结果转化为局部化、可归因的 harness 修改信号，从而获得真正可迁移的 harness 改进。

## 2. 方法论

### 核心思想
将任务级成功/失败信号通过**同一任务的对比轨迹分析**和**跨任务证据聚合**转化为功能模块级的演化信号，并将 harness 拆解为五个可独立演化的功能模块，在受限范围内修改后再整合。

### 关键流程（三阶段）

- **阶段一：对比轨迹采样与分析**
  - 对每个演化实例 $x_i$ 进行 K 次 rollout，得到轨迹 $(tra_i^1,\dots,tra_i^K)$，由任务专属 evaluator 给出二值奖励 $r_i^k$。
  - 按奖励将任务分为三组：
    - **Positive**（全部成功 $\sum_k r_i^k = K$）：分析执行质量与效率提升空间（冗余动作、重复探索）。
    - **Contrastive**（部分成功 $0<\sum_k r_i^k<K$）：配对同一任务的成功与失败轨迹，识别功能级差异因子。
    - **Negative**（全部失败 $\sum_k r_i^k=0$）：先查询轨迹记忆（Trajectory Memory）中历史成功轨迹进行配对；若无则做单侧诊断（重复循环、错误工具使用、无效恢复、过早终止等）。
  - 分析结果汇总为 JSON 结构化 findings，包含：所属模块、支撑轨迹证据、修改理由、建议修改。
  - 维护 **Trajectory Memory**，跨演化 epoch 存储历史轨迹与奖励，为当前 rollout 证据不足时提供额外对比证据。

- **阶段二：模块级 harness 修改**
  - **修改目标选择**：将指向同一函数的语义相似诊断合并为候选修改，按支持证据的**不同任务数投票**排序，优先处理跨任务支持的修改，降低实例特定失败的影响。
  - **演化历史（Evolution History）**：为每个被更新函数记录历史代码变更及其引入的功能，减少冗余/冲突修改，缓解演化震荡。
  - **五模块划分**：Agent Loop（迭代推理-行动-观测流程、重试与恢复）、Tool Use（工具选择/调用/校验）、Observation Management（环境反馈处理与压缩）、Context Management（交互历史维护、压缩、检索）、Task Completion Detection（完成判定）。
  - 各模块**独立并行演化，不共享中间更新**，且修改被限制在各自功能范围内。

- **阶段三：验证门（Validation Gates）**
  - **Program Check**：AST 校验、import 检查、协议合规、discovery-contract 验证、静态自属性审计；失败则按记录的 diff 回滚。
  - **Diff Review**：奖励盲审，检查修改是否编码任务特定解、启发式或条件，过拟合者拒绝回滚。
  - **Execution Validation**：从当前 batch 随机采样 2 个任务实际执行，若引入运行时错误或违反执行协议则回滚。

- **跨模块整合（Cross-Module Integration）**：五模块独立演化后组合为统一 harness，额外执行一个整合 epoch，识别并修复跨模块冲突（去除重复机制、厘清模块职责、调整协调逻辑）。整合后函数库**冻结**，下游评测期间不再修改。

- **函数库管理**
  - **Function Merge**：LLM 比较同模块内函数描述与行为，合并高度相似/重叠功能。
  - **Task-Aware Function Composer**：根据任务描述与候选函数描述，由 LLM 选择子集激活，使底层函数库可扩张而活跃 harness 保持紧凑。

## 6. 主要结论与发现

- **泛化性提升**：以 DeepSeek-V4-Flash-Preview 为骨干，域内设定下 TerminalBench 2.0 准确率从 47.57 → 52.43，SWE-Bench-Verified 从 73.40 → 76.45；TB 演化 harness 在 SWE-Bench 上达 75.80，SWE 演化 harness 在 TerminalBench 上达 49.40，表明学到的是可复用执行机制改进而非基准特化。
- **可靠性提升**：TerminalBench 2.0 的 Pass 3 从 30.34 → 35.96，说明演化还增强了多次试验下的一致性。
- **跨模型迁移**：冻结的演化 harness 在 GLM-5.2（59.55→61.80）、MiniMax-2.5（41.57→44.94）、DeepSeek-V4-Flash（47.57→52.43）上均一致提升。
- **模块化优于整体优化**：独立演化 + 整合取得最佳性能（52.43），而 Non-modular（46.44）与 Joint All-Module（44.19）甚至低于基线，说明限制修改范围可减少干扰。
- **模块互补性**：各单模块演化均优于基线；Agent Loop 带来最大单模块准确率增益，Observation Management 显著降低平均步数（34.70 → 22.50）。
- **对比分析有效**：随演化推进，可用对比轨迹对比例下降（Δ = −7.50 pp），说明 harness 逐步吸收了对比样例揭示的可复用改进。
- **数据难度影响**：中等难度为中心的分布优于 Hard & Easy 分布（SWE-Bench Verified 76.45 vs 74.25），因其提供更具信息量的成功-失败对比。
- **与已有方法对比**：在基准不相交协议下，AHE 与 Meta-Harness 仅比基线提升约 1 个百分点，而 ModularRSI 提升超过 5 个百分点。

## 7. 优点

- **问题定义清晰**：明确将 harness RSI 的困难拆解为数据、轨迹、机制三层挑战，并提出针对性设计。
- **基准不相交协议**：独立构建 2,000 个可执行演化任务，并做实例级相似度过滤与细粒度域分析，从流程上保证泛化评估的有效性，是可复用的标准化演化资源。
- **对比式信号提取**：同一任务成功/失败轨迹配对 + 跨任务证据聚合 + 投票排序，有效缓解实例特定噪声。
- **模块化与受限修改**：五模块独立演化减少跨机制干扰，配合演化历史、函数合并与任务感知组合器控制复杂度。
- **多重验证门**：程序检查 + 奖励盲 diff 审查 + 实际执行验证，兼顾可执行性、泛化性与正确性。
- **泛化验证充分**：同时覆盖未见域内任务、跨域任务与跨基座模型迁移，证据链较完整。

## 8. 不足与局限

- **算力信息缺失**：未披露 GPU 型号、数量与总时长，影响复现成本与效率评估。
- **对比分析缺少专门消融**：作者自述未隔离对比轨迹分析的独立贡献，其作用主要靠轨迹对比例趋势与案例研究间接支持。
- **演化规模受限**：主实验仅用 2,000 实例中的 240 个（每类 120 个），可能低估大规模演化数据的潜力。
- **案例研究非隔离**：前后对比中包含多个并发更新，无法归因单一修改的效果。
- **跨模型泛化仅在 TerminalBench 2.0 上验证**，未在 SWE-Bench 或其他域上系统检验。
- **评估器噪声风险**：案例研究（如 Scala→PySpark 任务）显示失败轨迹"功能等价且通过差分测试"，提示评估器侧可能存在噪声，可能污染演化信号。
- **应用限制**：方法依赖高质量可执行任务、可靠 evaluator 与多次 rollout 奖励，在缺乏这些条件的领域迁移性存疑；模块划分固定为五类，可能不适用于结构差异较大的 harness。
